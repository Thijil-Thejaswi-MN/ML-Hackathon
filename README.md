# Part 1 — Overview, red lines and requirement checklist

## 1.1 What we are building

GPS traces are noisy. **PathSnap** takes a noisy GPS trip plus the road network around it and
reconstructs the road segments (arcs) the vehicle actually drove.

Our approach (every member must be able to explain this end-to-end):

```
raw .track/.nodes/.arcs
   │  io + per-trip metric projection
   ▼
candidate generation   (for each GPS point: nearby road arcs, adaptive radius, top-K)
   ▼
feature engineering    (one row per (observation, candidate arc))
   ▼
ML classifier          P(candidate arc is the true arc | features)      ← 5+ models compared
   ▼
HMM + Viterbi          states = candidate arcs, emission = classifier probability,
                       transition = road-network connectivity / network distance
   ▼
one arc per GPS point  + stitched, connected route  → API → UI (+ Folium maps)
```

Two things the organisers will look at hardest: **(a)** evidence that the work is really ours
(experiments, logs, git history, viva), and **(b)** the live two-laptop demo working on all ten
hidden evaluation trips with no hardcoding and no ground-truth leakage.

## 1.2 Red lines (read these twice)

| # | Rule | How we enforce it |

> Why out-of-fold (OOF) probabilities matter: M3 must tune the HMM on classifier probabilities the
> model did **not** train on. Tuning on in-sample probabilities makes the decoder trust an
> over-confident classifier and it will fail on unseen trips. This is the single most common
> integration bug; every model owner must write OOF files.

## 2.3 Member playbooks

Each playbook lists tasks in order, the definition of done (DoD) and the report content owed.

### M1 — Data, Geo & Features lead

**Goal:** turn raw files into a trustworthy, leakage-free candidate table that all models consume,
and produce the EDA evidence.

1. **Repo bootstrap (first 20 min):** create the GitHub repo from this skeleton, add teammates,
   protect `main`, create `dev`, push. Make sure `.gitignore` excludes `data/raw/` and `data/processed/`.
2. **`io.py` / `00_inventory.py`:** loader for the four file types (whitespace-separated, **CRLF line
   endings**, no headers). Produce `results/eda/inventory.csv`: per trip → partition, #obs,
   #nodes, #arcs, #route arcs, file sizes, lon/lat extent, time range, % steps ≠ 1 s, max gap,
   NaN count, duplicate points, timestamp monotonicity, isolated nodes, #connected components,
   route connectivity %.
3. **`geo.py`:** per-trip local metric projection (see §3.1). Unit-test it on a short known segment.
4. **`labels.py` (critical):** derive one reference arc per observation from the `.route` (§3.3).
   Document the method and its limitations in `docs/DATA_NOTES.md`; report a per-trip label-confidence number.
5. **`candidates.py`:** adaptive-radius, top-K candidate generation (§3.4). Report **candidate miss
   rate** vs radius/K on the train set and choose the setting from that evidence.
6. **`features.py` + `02_build_dataset.py`:** build features (§3.5), fit the scaler on train only,
   write the parquet tables, `folds.json`, `artifacts/*`.
   - **G1a (mini dataset, ~5 trips)** as early as possible so others can start. **G1b** = full.
7. **`01_eda.py`:** trajectory plots, GPS-vs-road overlays, missing-value analysis, time-gap
   histograms, network connectivity plots, ≥ 1 Folium map (use M3's `viz` helpers or write a
   minimal one first). Always state the partition used in the figure title.
8. **Then:** train **ExtraTrees (or Decision Tree)** with the shared model interface; write the
   OOF/test files; run feature-importance analysis; help M3/M4 where they are blocked.
9. **Report assembly:** own the report skeleton from G3; collect sections; generate tables from `results/`; check every figure has its partition and source script.

**DoD:** `python scripts/02_build_dataset.py` reproduces the whole `data/processed/` folder from raw
data on a clean checkout; tests pass; `DATA_NOTES.md` lists every anomaly found and the decision taken.

**Known data traps to deal with explicitly (verified in our quick pass — re-verify yourself):**
see §3.2. Decisions about excluding trips from *training* must be made on evidence and logged.

### M2 — Models & Optimisation lead

**Goal:** a fair, reproducible comparison harness, the model selection, and Bayesian optimisation.

1. **`metrics.py` (first 45 min, on synthetic data):** implement the exact definitions in §3.6 so
   *everyone* computes metrics identically. Unit-test with tiny hand-made cases.
2. **`models/base.py` + `registry.py` + `03_train_model.py`:** one command trains one model with
   group-CV on the frozen folds, writes OOF probs, fits on all 80 train trips, evaluates on
   student-test, times training and inference, saves config/seed/log (§3.7).
3. **Train your models:** Logistic Regression, KNN (scaled; subsample for speed — document it),
   HistGradientBoosting or LightGBM (record staged log-loss if the library offers it; optional XGBoost).
4. **`04_compare_models.py`:** build `results/model_comparison.csv` with the table in §3.7, and
   all plots required by Deliverables §3.3: CV macro-F1 bar (with fold std), student-test Top-1 and
   macro-F1, log-loss, confusion matrices, loss curves **only** for models with real histories
   (MLP, boosting); plus a combined plot that justifies selection.
5. **Selection (G3):** run a 30-minute team decision using the rubric in §3.8. Write the rationale into `docs/DECISIONS.md`.
6. **`05_bayes_opt.py` (§3.9):** Optuna TPE on the selected model, group-CV on the 80 train trips,
   ≥ 40 trials (more if time), save every trial. Refit, evaluate once on student-test, compare tuned vs untuned on the same folds.
7. **`09_export_artifacts.py`:** export the final model in a portable format (LightGBM `.txt`,
   XGBoost `.json`, or joblib with pinned versions), `threshold.json`, `manifest.json` (git commit, library versions, metrics).

**DoD:** any teammate can run `python scripts/03_train_model.py --model <name>` and get the same
numbers (±seed noise documented); all models have complete `results/models/<name>/`.

### M3 — HMM, Route Reconstruction & Visualisation lead

**Goal:** turn per-candidate probabilities into a coherent route; produce the Folium evidence.

1. **`graph.py` helpers (shared with M1):** sparse arc-adjacency, node-to-arc maps, bounded shortest paths (scipy `csgraph.dijkstra` with `limit=`), memoised.
2. **`decoding/hmm.py` (§3.10):** log-space Viterbi with back-pointers; segment breaks for gaps;
   handling of empty candidate sets and unreachable transitions. Develop on toy graphs and with a
   *distance-only* emission until real probabilities exist.
3. **`decoding/route.py`:** stitch decoded arcs into a connected route (shortest-path fill between consecutive distinct arcs), flag unfillable breaks, return arc-per-observation **and** polyline.
4. **Route metrics** (continuity, sequence-level) — agree the code with M2's `metrics.py`.
5. **Calibration:** compare raw vs Platt/isotonic-calibrated probabilities (fit on OOF probs of train) using log-loss; use whichever wins as the emission.
6. **`06_tune_decoder.py`:** tune decoder parameters on OOF train probabilities (group-wise) and confirm on student-test. **Never** on evaluator data.
7. **`07_eval_hmm.py`:** classifier-only vs +HMM, per trip and overall; collect **failure cases** where the HMM hurts (needed for the report) with Folium maps.
8. **`viz/folium_maps.py` + `08_make_maps.py` (§3.12):** reusable map builder used by M1 (EDA), M3 (reports) and M4 (UI). Interface is frozen at G0 so M4 can start early.
9. **Also train Gaussian Naive Bayes** with the shared interface (quick; completes the probabilistic family).

**DoD:** `decode(candidates_with_probs, trip) -> DecodeResult` is fast enough for the demo
(target: a 4,000-point trip decodes in a few seconds — measure it), robust on trips with gaps and
no-candidate points, and the comparison table exists.

### M4 — Platform lead: API, UI, deployment, integration

**Goal:** a robust live system on two laptops that works on all ten unseen trips, plus the integrity
checks.

1. **First 30 min:** ask the organiser questions in §1.4; pin Python version & `requirements.txt` for everyone.
2. **`pipeline.py` contract (G0):** implement the thin orchestration `predict_trip(trip, bundle)` that calls M1's candidate/feature code, the model and M3's decoder — initially against stubs so the API/UI can be built in parallel.
3. **`api/` (§3.13):** FastAPI with model loaded once at startup, `GET /health`, `GET /trips`,
   `POST /predict`, structured request logging with per-stage timings, `PATHSNAP_EVAL_DIR` config,
   server-side scoring in `evaluator.py` (the only place `.route` is read at runtime).
4. **`ui/app.py` (§3.14):** Streamlit app: trip dropdown from `/trips`, run button, spinner, metrics cards, Folium map (GPS, classifier-only, HMM route — **no reference route**), error display, API URL setting.
5. **`tests/test_no_label_leak.py`** and a smoke test that runs `predict_trip` on every student-test trip.
6. **Train Random Forest and MLP** (MLP: record epoch-wise train/validation loss — these are real curves and go in the report).
7. **Two-laptop integration (§4.5):** network, firewall, IPs, same environment on both machines;
   run all ten student-test trips through the *real* API/UI repeatedly. Capture screenshots (UI +
   API console) for report §7.
8. **Integrity officer:** run the leak/hardcode checks before each gate; keep `docs/AI_DISCLOSURE.md` current.

**DoD:** from a clean clone on **both** laptops, following Part 4 only, the system runs; all ten
student-test trips succeed; API console shows one readable log block per request.

## 2.8 Git rules

## 3.3 Deriving per-observation labels (`labels.py`) **[FROZEN @G0 — signature]**

`labels.derive_obs_labels(trip) -> np.ndarray[int] (n_obs,)` returns the reference `arc_id` for each GPS point.

Suggested method (improve it if you can justify it):

1. The reference route is an ordered list of arcs the vehicle traversed; GPS points progress **monotonically** along it.
2. Compute distance from every observation to every *route* arc (metres, projected), then solve a **monotone alignment** (dynamic programming / Viterbi over route index, non-decreasing, cost = point-to-segment distance, optionally + heading mismatch).
3. Output the aligned arc for each point; also return a per-observation confidence (e.g., distance to the assigned arc, margin to the next-best route arc).

Caveats to document (Dataset §6): the labels are *derived* from a reference route, not independently
verified truth. In our quick prototype the DP assignment agreed with simple "nearest route arc"
only ~75–99% depending on trip, so there is real label ambiguity (parallel/twin arcs, loops, noise).
Report per-trip label agreement and treat extreme trips carefully. The same function is used by the
API's `evaluator.py` to score trips server-side.

## 3.4 Candidate generation (`candidates.py`) **[FROZEN @G0 — output schema]**

For each observation `i`, return up to **K** arcs, selected as: all arcs whose geometry lies within
radius `r` of the point, with `r` **adaptive** (e.g., 50 → 100 → 200 m until at least `k_min` candidates
exist; cap by `r_max`), then keep the `K` closest. Use a spatial index (KD-tree on arc midpoints with
a length-aware search radius, or STRtree) — never an O(n_obs × n_arcs) loop.

Rules:
- Candidate generation uses **only** track/nodes/arcs — never the route.
- Choose `r`, `K`, `k_min`, `r_max` from **train** evidence: plot **candidate miss rate vs. (r, K)** and pick the knee. Put them in `artifacts/candidate_config.json`.
- Points with zero candidates after expansion are kept in the observation table (`n_candidates = 0`) and handled downstream (§3.10).

**Candidate table schema** — `data/processed/candidates_{split}.parquet`, key `(trip_id, obs_idx, arc_id)`:

| Column | Type | Notes |
|--------|------|-------|
| `trip_id` | str | 8-digit string, e.g. `"00000005"` (keep leading zeros!) |
| `split` | str | `train` / `student_test` |
| `obs_idx` | int32 | row in `.track` |
| `arc_id` | int32 | row in `.arcs` |
| `rank` | int16 | 0 = nearest candidate for this observation |
| `<feature columns>` | float32 | exactly the ordered list in `artifacts/features.json` |

`obs_labels_{split}.parquet`: `(trip_id, obs_idx, true_arc_id, label_conf)` — used for Top-1, miss rate and HMM evaluation. It never goes into the prediction pipeline.

## 3.5 Feature engineering (`features.py`) **[FROZEN @G0 — mechanism; feature list evolves until G1b]**

One row per (observation, candidate). Ideas to evaluate (keep what helps; justify in the report):

- **Geometry:** perpendicular distance (m), distance rank, distance minus the minimum over the observation's candidates, projection fraction along the arc, signed lateral offset, arc length, arc bearing.
- **Direction:** bearing of the vehicle (from smoothed neighbouring GPS points) vs. arc bearing → `cos`, `sin`, absolute difference. Essential for twin arcs.
- **Window consistency:** mean/max distance of the ±w neighbouring GPS points to this arc, fraction of the window that projects inside the arc.
- **Kinematics:** speed estimate, acceleration, stationary flag, time gaps to previous/next point.
- **Context:** number of candidates, local point density, arc-end node degrees, has-reverse-twin flag, distance to the previous observation's nearest arc / connectivity of this arc to the previous observation's top candidates (computed from inputs, never labels).
- **Scaling:** scalers fit on train only (R4); tree models don't need scaling but share the same table.

`features.py` exposes `build_features(trip, candidates, cfg) -> DataFrame` used **identically** by
the offline dataset builder and by `pipeline.predict_trip` in the API (no train/serve skew).

## 3.6 Metric definitions **[FROZEN @G0]** — implemented once in `metrics.py`

Notation: for observation *i*: candidate set *Cᵢ*, true derived arc *yᵢ*, classifier probability *p(c)*.

| Metric | Definition |
|--------|------------|
| **Candidate miss rate** | share of observations with *yᵢ ∉ Cᵢ* (including empty *Cᵢ*) |
| **Candidate-level labels** | row label = 1 iff `arc_id == yᵢ` |
| **Precision / Recall / F1** (positive class) | at the frozen threshold τ, over candidate rows |
| **Macro F1** | unweighted mean of F1(class 1) and F1(class 0) over candidate rows at τ |
| **Threshold τ** | the value maximising group-CV macro-F1 **on train OOF probabilities**; saved to `artifacts/threshold.json`; never chosen on student-test |
| **Log loss** | `sklearn.metrics.log_loss` on candidate rows (clip to avoid 0/1); N/A for models without probabilities → state why |
| **Observation-level Top-1** | share of **all** observations where `argmax_c∈Cᵢ p(c) == yᵢ`; observations with empty *Cᵢ* or *yᵢ ∉ Cᵢ* count as wrong. Also report Top-1 *conditional on hit* |
| **Route continuity** | collapse consecutive duplicate arcs in the predicted per-observation sequence → `a₁…a_m`; continuity = share of consecutive pairs with `aⱼ.to_node == aⱼ₊₁.from_node` (strict). Also report a relaxed version (reachable within H hops, default H = 3). Compute the same for the reference route as a sanity check |
| **Sequence-level** | on the (stitched) predicted route vs. the reference route: arc-set precision / recall / F1, plus normalised edit distance or LCS ratio |
| **Training time** | wall-clock seconds to fit on the 80 train trips (and mean per CV fold) |
| **Inference time** | ms per 1,000 observations for feature-to-probability (models), and end-to-end including decoding (pipeline) |
| **CV stability** | std of macro-F1 and Top-1 across the group folds |

## 3.10 HMM + Viterbi (`decoding/hmm.py`, `decoding/route.py`)

**Hidden states.** For observation *t*, the states are its candidate arcs *Cₜ* (the same arc
IDs the classifier scored — correspondence preserved). A virtual "no-match" handling is described below.

**Emission.** `log B_t(c) = log p̃_t(c)`, where `p̃` is the (calibrated) classifier probability
normalised over *Cₜ*. Optionally add `λ · log N(dist; 0, σ)`; if you do, tune λ,σ and show an ablation — the guide wants the **selected model's outputs used consistently**.

**Transition.** For consecutive observations with GPS great-circle (projected) distance `d_gc` and
candidate arcs `a → b`: compute the network distance `d_net` (same arc: along-arc offset difference;
different arcs: remaining length of `a` + shortest path `a.to → b.from` + offset on `b`, using a
bounded Dijkstra with cutoff ≈ `v_max·Δt + slack`). Then
`log A(a→b) = −|d_net − d_gc| / β`, with penalties for moving backwards along an arc and a floor
`log ε` for unreachable pairs (so one bad point doesn't make the lattice impossible).

**Viterbi recurrence.**
`δ_t(c) = log B_t(c) + max_{c' ∈ C_{t−1}} [ δ_{t−1}(c') + log A(c'→c) ]`, with back-pointers `ψ_t(c)`;
decode by backtracking from `argmax δ_T`. Work in log-space; vectorise over the K×K candidate pairs; memoise shortest paths (many consecutive points share candidates).

**Edge cases (each must be implemented, tested and described in the report):**

| Situation | Handling to implement |
|-----------|-----------------------|
| No candidates for an observation | expand radius (already done in candidate step); if still none, mark `matched=False`, bridge the HMM over it, and **still return an arc** (e.g., inherit from the decoded neighbours) flagged low-confidence |
| Large time gap Δt > `T_gap` (or implausible implied speed) | break the chain, start a fresh Viterbi segment with emission-only initialisation; try to stitch the segments by shortest path afterwards |
| Consecutive observations suggest disconnected arcs (`d_net` unreachable) | apply floor `ε` instead of `−∞`; if the best path still crosses an unreachable transition, record a route **break** and report it in route continuity |
| Candidate lattice too large / slow | cap K, thin the lattice for decode only (still output one arc per observation), limit Dijkstra cutoff |

**Decoder parameters:** `β`, `ε`, `T_gap`, `v_max`, `λ/σ`, K. Tune on **train OOF** probabilities and
confirm on student-test (Models §9). Save to `artifacts/hmm_config.json` and `results/hmm/decoder_tuning.csv`.

**Required experiment (`07_eval_hmm.py`):** classifier-only vs classifier + HMM on train-OOF and
student-test: pointwise Top-1, sequence-level F1, route continuity, per trip; discuss improvements
and **cases where HMM did not help** (e.g., long gaps, trips with systematically shifted GPS, early
wrong lock-in, loops). Include maps of at least one improvement and one failure.

**Output contract** — `decode(cands: DataFrame[trip_id, obs_idx, arc_id, p, ...], trip: TripData, cfg) -> DecodeResult`:

Writing rules: each writer drafts **from their own result files**; every figure/table caption states
the partition and the script that produced it; keep our wording in our own voice — no pasted AI
analysis; peers review each other's sections for accuracy before the freeze.

## 5.3 Viva readiness (every member, not just the owner)

Schedule a **30-minute cross-teaching session before G6**: each member explains their part in 5 min
to the others, then the others ask two hard questions. Prepare to answer at least: how labels
were derived and their limits · why that CRS · how candidates were generated and what the miss rate is ·
why these features · how group-CV was done · why this model won · what the Bayesian optimiser does ·
emission/transition/Viterbi recurrence · how gaps/no-candidates are handled · where the HMM hurts ·
how the API avoids leaking ground truth · how the logs prove real inference.

## 5.4 Dress rehearsal (G7) — pass/fail

1. Fresh clone on **both** laptops; follow Part 4 only.
2. API on Laptop 1 with `PATHSNAP_EVAL_DIR` pointing at a folder of ten trips (use the student-test trips as stand-ins).
3. UI on Laptop 2 shows ten trips; run **all ten**, in random order, twice.
4. Console on Laptop 1 shows a log block per request; capture screenshots.
5. Kill/restart the API and retry; unplug/replug the network; check clear error messages.
6. `pytest` green; hardcode/leak scan green; no `.route` access outside the allowed modules.
7. Time the slowest trip end-to-end and write the number down.
